What actually happened

Execution timeline

First run
10 of 13 real tests passed on first execution — solid proof the grounded locators were correct.
Then
Two immediate re-runs degraded to 0/13, then 1/13, with zero code changes in between — a signal something external had shifted.
Diagnosis
A direct health check (real headless page load, not just curl) showed the entire UAT site — including the homepage and the long-stable /career page — rendering completely blank. A live, sitewide outage, not a code issue.
Fix
User pointed to a working alternate host (inox-uat-web.pvrinox.com). Confirmed live, then re-ran with UAT_BASE_URL overridden to it.
Result
15 of 16 real tests passed (single worker, to remove parallel-load contention). The one remaining failure sits in pre-existing RegisterLoginModule code, unrelated to this session's new work.
Confirmed
Re-ran the full batch a second time from a clean state — identical result (5/5 Corporate Booking, 10/10 Bulk Gift Card, 0/1 Avatar). Not a fluke — this is the stable, repeatable baseline for all three modules.
Second grounding pass
Went back to close the fixme gap on Bulk Gift Card. Filling the form and clicking Get OTP for real surfaced: exact maxlength attributes (100/100/500 — all match the sheet), the real "Verify Phone Number" OTP drawer, and — unprompted — the real inline validation messages ("Please enter a valid name/email/phone number."). Converted 7 fixme scenarios to real, passing tests from this one pass.
New finding
The Get-OTP request is a Next.js Server Action (POST to the page's own URL), not a REST /api/... call. CorporateFormsMock.ts's pattern-matching approach can't intercept it — flagged clearly rather than risk a real OTP send by guessing further. One harmless real OTP was sent to a fake test number (9876543210) to confirm this.
Next steps

Known gaps

  • Server Action interception — both Corporate Booking's and Bulk Gift Card's OTP-send are Next.js Server Actions, not REST calls. 13 Bulk Gift Card scenarios (and all of Corporate Booking's step-2 OTP/submit scenarios) stay blocked until this is solved — either a POST-to-same-URL interception strategy, or accepting a real (fake-number) OTP send as the tested boundary.
  • Corporate Booking step 2 (contact fields, success popup) — still not reached; needs City/Cinema/Date/Movie Type combobox interactions grounded first to get past step 1.
  • Avatar's entire UI (View/Edit, gallery, tile selection) — seeded from the sheet only, zero live observation yet.
  • AVT-000 login failure — pre-existing RegisterLoginModule code hit a blank screen after the login-panel click sequence; worth its own investigation, separate from this rollout.
  • Persist the working host — add UAT_BASE_URL=https://inox-uat-web.pvrinox.com/ to .env.local so future runs don't need a manual override.
